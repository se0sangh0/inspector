## 0. 앞선 진단 정정

이전 보고에서 "게임 코드가 용어 사전의 비권장 표기를 쓰고 있다 · 13개 파일"이라고 했습니다.
**이 진단은 틀렸습니다.**

Notion `02. 동료 · 적 · 데이터`는 다음을 명시합니다.

> 캐스터 / 오펜더 / 디펜더 / 어택커 / 프리스트 / 샤먼은 **데이터 연결용 내부 직업 ID**다.
> **UI에는 세계별 표시 직업명을 사용**하고 외형·스킬명·아이콘·VFX도 테마별 L1 변형을 적용한다.

`13. 서사 설정(내부)`도 "내부 직업 ID … 데이터 연결용 내부 ID로 유지"라고 못 박습니다.

즉 설계는 **2층 구조**입니다.

| 층 | 값 | 용도 |
| --- | --- | --- |
| 내부 직업 ID | 캐스터·오펜더·디펜더·어택커·프리스트·샤먼 | 데이터 연결 |
| 표시 직업명 | 원소술사·척살자·봉쇄병·돌격병·치유사·주술사 | 화면 노출 |

용어 사전의 `비권장 표기`는 **표시 직업명**에 적용되는 규칙이며, 내부 ID에는 적용되지 않습니다.
따라서 코드와 데이터가 내부 ID로 `캐스터`를 쓰는 것은 **정상**입니다.

**진짜 문제는 내부 ID가 화면으로 새어 나오는 지점 3곳입니다.**

---

## 1. 목표

내부 직업 ID가 플레이어 화면에 노출되지 않게 하고, 마석 상점을 영어로 읽을 수 있게 합니다.

**성공 기준**

1. 한국어 모드에서 동료 이름이 `원소술사·척살자·봉쇄병·돌격병·치유사`로 표시된다
2. 영어 모드에서 동료 이름이 `Elementalist·Executioner·Blockade Soldier·Shock Trooper·Healer`로 표시된다
3. 영어 모드에서 마석 상점에 한국어가 남지 않는다
4. 내부 직업 ID(`jobClass`)와 데이터 연결은 바뀌지 않는다

## 4. 작업 2 · 번역표의 동료 직업명 교체

### 현재 상태

`LocalizationTable.cs`가 **내부 ID를 번역 키로** 씁니다.

```csharp
// 동료 직업명
Add("캐스터", "Caster");
Add("오펜더", "Offender");
Add("디펜더", "Defender");
Add("프리스트", "Priest");
Add("어택커", "Attacker");
Add("샤먼", "Shaman");
```

작업 1로 `displayName`이 바뀌면 이 키는 더 이상 매칭되지 않아 **영어 모드에서 한국어가 그대로 남습니다.**
두 작업은 같은 커밋에서 함께 처리해야 합니다.

### 변경 후

```csharp
// 동료 표시 직업명
Add("원소술사", "Elementalist");
Add("척살자", "Executioner");
Add("봉쇄병", "Blockade Soldier");
Add("돌격병", "Shock Trooper");
Add("치유사", "Healer");
Add("주술사", "Shaman");
```

### 영문 표기 근거

`용어 사전`의 `영문·코드` 필드는 `표시용 / 코드용` 두 형태를 담습니다.
공개 페이지는 **표시용(앞쪽)** 형태로 이미 통일했습니다 (커밋 `06fc8ad`).
게임 화면도 같은 기준을 적용해 공개 페이지와 일치시킵니다.

| 표시 직업명 | 용어 사전 `영문·코드` | 채택 |
| --- | --- | --- |
| 원소술사 | Elementalist / Caster | Elementalist |
| 척살자 | Executioner / Offender | Executioner |
| 봉쇄병 | Blockade Soldier / Defender | Blockade Soldier |
| 돌격병 | Shock Trooper / Attacker | Shock Trooper |
| 치유사 | Healer / Priest | Healer |
| 주술사 | Shaman | Shaman |

### 주의

기존 키(`캐스터` 등)를 지울지 남길지 결정이 필요합니다.
**남기기를 권장합니다.** 어딘가에서 내부 ID가 화면에 노출되는 경로가 더 있을 경우 폴백으로 작동합니다.

## 5. 작업 3 · 마석 상점 패시브 설명의 내부 ID 제거

`MetaPassiveManager.cs`의 `desc`는 플레이어에게 보이는 설명 문구인데 내부 ID가 들어 있습니다.

**예시** (`MetaPassiveManager.cs:90`)

```csharp
new Info{ id=CasterAmp, kind=Kind.Passive, job="캐스터", name="주문 증폭",
          desc="캐스터가 주는 모든 데미지 +15%", cost=80 },
```

- `job="캐스터"` → **유지** (내부 ID로 쓰는 데이터 필드)
- `desc="캐스터가 주는…"` → **`"원소술사가 주는 모든 데미지 +15%"`로 교체**

`desc`와 `name` 전체를 훑어 내부 ID가 들어간 문구를 모두 표시 직업명으로 바꿉니다.

## 6. 작업 4 · 마석 상점 문자열 번역표 등록

번역표에 `영혼석` 항목은 7건 있으나 **`마석` 항목은 0건**입니다.
영어 모드에서 마석 상점만 한국어로 표시됩니다.

### 등록 대상 (확인된 것)

**`마석`의 영문 표기는 `ManaStone`으로 확정합니다** (2026-09-04 사용자 결정).

| 한국어 | 영문 |
| --- | --- |
| `보유 마석: {0}` | `ManaStone: {0}` |
| `마석 +{0}` | `ManaStone +{0}` |
| `마석 -{0}` | `ManaStone -{0}` |
| `마석 0` | `ManaStone 0` |
| `재화(영혼석/마석)` | `Currency (Soulstone / ManaStone)` |

### 규칙

- 서식 문자열은 `Loc.Tr(키, args)` 호출로 처리합니다. 문자열 매칭으로는 잡히지 않습니다
- 위 목록은 검색으로 찾은 것이며 누락이 있을 수 있습니다. **영어 모드로 마석 상점을 열어 남은 한국어를 모두 찾아 등록합니다**
- 작업 3에서 바꾼 `desc`·`name` 문구도 번역표에 등록합니다
- 한국어 표시는 `마석`을 유지합니다. `마나석`은 쓰지 않습니다 (용어 사전 확정 표기는 `마석`)
- 클래스명 `MagicStoneShopPanel`은 이번 범위에서 바꾸지 않습니다. MonoBehaviour 이름 변경은 씬 참조에
  영향을 주므로 별도 안건으로 다룹니다

## 7. 완료 조건과 검증

### Given–When–Then

**QA-01 · 한국어 표시 직업명**
- Given: 언어가 한국어인 상태로 새 런을 시작한다
- When: 전투에 진입해 동료 이름이 보이는 화면과 전투 로그를 확인한다
- Then: `원소술사·척살자·봉쇄병·돌격병·치유사`가 표시된다. `캐스터·오펜더·디펜더·어택커·프리스트`는 화면에 나오지 않는다

**QA-02 · 영어 표시 직업명**
- Given: 설정에서 언어를 영어로 바꾼다
- When: 같은 화면을 확인한다
- Then: `Elementalist·Executioner·Blockade Soldier·Shock Trooper·Healer`가 표시된다

**QA-03 · 마석 상점 영문화**
- Given: 언어가 영어인 상태다
- When: 좌측 패널 토글 또는 메타 상점 버튼으로 마석 상점을 연다
- Then: 패널 안에 한국어가 남아 있지 않다. 패시브 이름·설명·보유량 표시가 모두 영어다

**QA-04 · 내부 ID 연결 유지**
- Given: 작업 완료 후 새 런을 시작한다
- When: 각 동료의 스킬 발동과 애니메이션을 확인한다
- Then: 스킬·애니메이터·스프라이트가 이전과 동일하게 작동한다. `jobClass` 기반 로직에 오류가 없다

**QA-05 · 언어 전환 즉시 반영**
- Given: 마석 상점이 열려 있다
- When: 설정에서 언어를 바꾼다
- Then: 열려 있는 패널의 문구도 함께 바뀐다
- 참고: `LocalizationManager.OnLanguageChanged` 구독처가 현재 0건입니다. 이 항목이 실패하면 구독 연결이 필요합니다

### 회귀 확인

- 세이브 호환성: `displayName`은 표시 전용이므로 저장 계약에 영향이 없어야 합니다. 저장 데이터에 `displayName`을 기록하는 경로가 있는지 확인합니다
- `MercenaryService`의 후보 풀 생성이 `jobClass` 기준으로 계속 동작하는지 확인합니다

### 11.6. 새로 발견 — 이번 범위 밖의 잔여 누출

`MercenaryService`가 모집·방출·판매 기록을 만들 때 **내부 ID를 화면 문자열에 함께 넣습니다.**

```
MercenaryService.cs:200  $"{candidate.displayName} ({candidate.jobClass} | {candidate.starLevel}★) ..."
MercenaryService.cs:342  $"{fellow.displayName} ({fellow.jobClass} | {fellow.starLevel}★) 방출 (환급 없음)"
MercenaryService.cs:363  $"{fellow.displayName} ({fellow.jobClass} | {fellow.starLevel}★) 판매"
```

이 문자열은 `RecordRecruitment()` → `RunSessionManager.AddRecord(RunRecordType.RecruitmentResolved, ...)`
경로로 **조사관 수첩과 탐사 보고서에 기록**됩니다.

**영향 2가지**

1. `displayName`을 고쳐도 수첩에 `원소술사 (캐스터 | 1★)` 처럼 내부 ID가 **괄호로 계속 노출**됩니다
2. 이 문자열은 보간으로 생성되므로 번역표 자동 스캔이 잡지 못합니다.
   영어 모드에서 수첩의 모집 기록이 **한국어로 남습니다**

**조치**: 이번 스펙 범위 밖이므로 고치지 않고 보고만 합니다 (§10.7).
별도 안건으로 다룰지 결정이 필요합니다.
