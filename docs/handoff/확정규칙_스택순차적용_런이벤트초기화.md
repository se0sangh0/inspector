# 확정 규칙 반영 — 스택 순차 적용·새 런 이벤트 초기화

- 작성일: 2026-09-27
- 상태: 로컬 구현·컴파일·PlayMode API 회귀 검증 완료. 전체 플레이 흐름은 미검증.
- 요청: 문서를 확인해 추가 기획 결정 없이 가능한 Unity 작업부터 진행한다.
- 시작 코드: `e9c3021` · 작업 시작 시 추적 파일 변경 없음
- 대상: 현재 6층 프로토타입

## 1. 목표와 근거

카드의 선택 순서가 스택 결과에 반영되게 한다.
새 탐사에는 이전 탐사의 이벤트 추첨 기록을 넘기지 않는다.

- [01. 전투·카드·스트레스](https://app.notion.com/p/3af6aef5baac81788f2aef36ab709084) §2-1a:
  2026-09-22 확정. 카드마다 순서대로 계산하고 매번 0 하한을 적용한다.
- [전시 이후 개발 계획](https://app.notion.com/p/3e16aef5baac81c1bdb8fcc41b0bf979) §2:
  현재 전체 합산 코드를 확정 규칙과 다른 구현으로 추적한다.
- [16-B. 구현·데이터 계약](https://app.notion.com/p/3b96aef5baac8105a571f6f75cc00376) §4:
  `StartNewRun()`이 새 런 상태를 초기화한 뒤 진행을 연다.
- `EventCatalog.ResetRun()`의 런별 소비 기록 계약과
  [2026-09-13 점검 F-01](../project-audit/2026-09-13_Unity_점검_인계.md):
  `ResetRun()`은 정의돼 있지만 새 런 진입점에서 호출되지 않았다.

Notion 원문은 2026-09-27에 직접 다시 조회했다.
이번 작업은 확정 규칙의 구현 수정이며 새 기획 결정은 없다.

## 2. 수정 범위

| 파일 | 변경 |
|---|---|
| `Assets/Scripts/GameManager.cs` | 턴 시작 스택부터 선택 목록 순서대로 계산하고 카드마다 0 하한 적용 |
| `Assets/Scripts/Run/RunSessionManager.cs` | 초기화 성공 후 세션 활성화 전에 `EventCatalog.ResetRun()` 호출 |

취소는 감소량을 역산하지 않고, 남은 선택 목록을 턴 시작값부터 다시 계산한다.
취소한 카드를 다시 선택하면 목록의 끝에서 적용한다.
턴 종료는 이미 반영한 스택을 유지하고 선택 카드만 소비한다.

## 3. 완료 조건

| 시작 상태와 행동 | 기대 결과 |
|---|---|
| 스택 0에서 −2 → +3 | 0 → 3 |
| 스택 0에서 +3 → −2 | 3 → 1 |
| 스택 2에서 −5 → +4 | 0 → 4 |
| 위 선택에서 −5를 취소 | 6 |

| 선택 전부 취소 | 턴 시작 스택 복원 |
| 서로 다른 역할 카드 선택 | 각 역할 스택을 독립 계산 |
| 턴 종료·중복 소비 호출 | 카드 소비 후 스택 재적용 없음 |
| 다음 턴 시작 후 선택·취소 | 이월된 스택이 새 계산 기준 |

| 마감 전 새 런·승리 후 새 런·전멸 후 새 런 | 이전에 뽑은 이벤트를 다시 뽑을 수 있음 |
| 마감 전 새 런·중복 마감 | 완료 런 수에 잘못된 증가 없음 |

검증은 Unity 6000.3.9f1의 별도 프로젝트 사본에서 수행한다.
검증 사본은 별도의 제품명·회사명을 사용해 저장 데이터를 분리한다.
게임 코드와 리소스는 원본에서 복사하고 변경 파일의 해시를 비교한다.

## 5. 검증 결과

Unity 6000.3.9f1에서 같은 검증 코드로 수정 전후를 비교했다.
검증 코드가 PlayMode에서 실제 게임 컴포넌트와 리소스를 호출했다.
계산 로직을 다른 언어로 복제하거나 런 초기화를 모의 객체로 바꾸지 않았다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| C# 컴파일 오류 | 0 | 0 |
| 검증 단언 36개 | 통과 30·실패 6 | 통과 36·실패 0 |
| 검증 실행 중 예상 밖 오류 | 0 | 0 |
| Unity 종료 코드 | 1 — 기대값 불일치 | 0 |
| 0에서 −2 → +3 | 1 — 실패 | 3 — 통과 |
| 2에서 −5 → +4 | 1 — 실패 | 4 — 통과 |
| 중단·승리·전멸 뒤 새 런의 이벤트 추첨 | 앞 런에서 뽑은 이벤트 제외 | 동일 시드로 같은 이벤트 재추첨 |

취소·재선택, 역할별 계산, 카드 소비, 다음 턴의 이월 기준,
이벤트 정의 캐시 유지와 완료 런 수의 1회 증가도 통과했다.
수정 전 실패 6개는 스택 관련 단언 3개와 런 경계 관련 단언 3개다.
검증 사본의 두 변경 파일이 원본과 같은지 SHA-256으로 확인했다.
별도 읽기 전용 코드 검토에서도 추가 수정 사항이 없었다.

최초 사본 불러오기에서 Unity 검색 인덱스의 예외가 발생했다.
그 실행은 결과로 세지 않았다. 검증 예약 방식을 `delayCall`에서
`update`로 바꾼 뒤 동일한 검증 코드를 수정 전후 모두 다시 실행했다.
생산 코드와 프로젝트 설정에는 이 대응을 넣지 않았다.

### 증거와 재실행

로컬 전용 증거: `_workspace/2026-09-27-unity-confirmed-rules/`

- `before.json` / `after.json`: 36개 항목의 기대값·실제값·통과 여부.
- `before-editor.log` / `after-editor.log`: 컴파일·플레이 모드·종료 로그.
- `before-initial-import.log`: 최초 불러오기에서 발생한 편집기 예외 기록.
- `ConfirmedRulesChecks.cs`: 별도 사본에만 넣은 검증 코드.
- `source-hashes.json`: 시작 커밋·변경 파일·검증 코드의 해시.
- `validation-project.txt`: 검증 사본의 실제 경로.

재실행 시 별도 사본의 `Assets/Editor/`에 검증 코드를 넣는다.
사본의 회사명은 `CodexIsolatedValidation`, 제품명은
`InspectorConfirmedRules20260927`로 두어 저장 데이터를 분리한다.
`INSPECTOR_RULES_RESULT` 환경변수에 결과 JSON의 절대 경로를 지정한다.
Unity에 `-batchmode -nographics -projectPath <사본 경로>`와
`-executeMethod ConfirmedRulesChecks.RunBatch -logFile <로그 경로>`를 전달한다.
플레이 모드 검증 후 자체 종료하므로 `-quit`은 붙이지 않는다.
