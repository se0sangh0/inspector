## 0. 이 문서를 쓰는 사람이 먼저 알아야 할 것

**이 머신에는 C# 컴파일러도 Unity Editor도 없다.** `dotnet` / `mcs` / `csc` /
`mono` 모두 없고 `/Applications/Unity/Hub/Editor/`도 비어 있다. 그래서 아래
내용은 전부 **소스 정적 분석**이며, 컴파일·플레이 검증을 거치지 않았다.
AGENTS.md §7이 요구하는 "C# 변경은 최소한 Unity 컴파일 오류가 없는지 확인"을
만족할 수 없어 코드 수정을 하지 않았다.

수정을 맡는 사람은 Unity 6000.3.9f1에서 컴파일과 플레이 확인을 반드시 거친다.

## 1. F-01 · 런을 새로 시작해도 이벤트 소비 기록이 초기화되지 않는다

| | |
|---|---|
| 확실성 | **확정.** grep으로 호출자 0개 확인 |
| 영향도 | **높음 — 전시 시연 품질에 직결** |
| 성격 | 배선 누락(객관적 결함) |

### 근거

`EventCatalog.ResetRun()`은 정의돼 있지만 **호출하는 곳이 없다.**
저장소 전체에서 이 이름이 나오는 곳은 두 군데뿐이다.

```
Assets/Scripts/Event/EventCatalog.cs:14   // 문서 주석
Assets/Scripts/Event/EventCatalog.cs:54   // 정의
```

소비 기록은 정적 필드라 앱 프로세스 전체에서 살아 있다.

```csharp
// Assets/Scripts/Event/EventCatalog.cs:25
private static readonly HashSet<string> _consumed = new(); // 이번 런에서 소비한 이벤트 id
```

주석은 "이번 런에서 소비한"이라고 적혀 있지만 실제로는 런 경계를 넘는다.
`EventCatalog.cs:14`의 자체 계약도 `ResetRun() : 새 런 시작 시 소비 기록 초기화`로
호출을 전제한다.

런 초기화 단일 창구인 `RunSessionManager.StartNewRun()`
(`Assets/Scripts/Run/RunSessionManager.cs:184`)은 네 가지를 초기화하지만
이벤트 카탈로그는 건드리지 않는다.

1. `MercenaryService.ResetForNewRun()`
2. `PartyManager.SetupInitialParty()`
3. `SoulstoneManager.ResetCurrency()`
4. `Records` / `PendingObservationId` / `_battleRecordedFloors` / `_runResolvedRecorded`

### 재현 절차

1. 앱을 실행하고 런 1을 시작한다.
2. `?` 노드에 진입해 이벤트를 하나 본다. 어떤 이벤트였는지 적어 둔다.
3. 런을 마감하거나 디버그 패널의 `새 런 시작`으로 런 2를 시작한다.
   **앱은 끄지 않는다.**
4. `?` 노드에 반복 진입한다. 2단계에서 본 이벤트는 후보에서 빠져 있다.

### 증상

부스에서 앱을 껐다 켜지 않고 시연을 반복하면 런이 거듭될수록 이벤트 후보가
줄어든다. 특히 **새 삽화를 넣은 EVT-01 `식어 있는 야영지`가 그 삽화를 뽑은
첫 런 이후 다시 나오지 않는다.** 후보가 완전히 소진되면
`GetRandom`의 소프트락 방지 분기(`EventCatalog.cs:79`)가 `_consumed`를 비워
순환을 재시작하므로 진행이 막히지는 않는다.

### 제안하는 수정

`StartNewRun()`의 ④ 다음, 세션 활성화 직전에 한 줄을 넣는다.

```csharp
// ⑤ 선택지 이벤트 소비 기록 초기화 — 런 안에서만 중복을 막는다.
//    비우지 않으면 앞 런에서 뽑힌 이벤트가 다음 런에서 후보에서 빠진다.
EventCatalog.ResetRun();
```

기존 `// ⑤ 세션 활성화` 주석은 `⑥`으로 바꾼다.

**컴파일 위험은 사실상 없다.** `EventCatalog`와 `RunSessionManager` 모두 전역
네임스페이스이고, 저장소에 `.asmdef`가 없어 단일 `Assembly-CSharp`에 들어간다.
`public static void ResetRun()`이라 using 추가도 필요 없다.

### 함께 처리할 문서 미결

`RunSessionManager.cs:13-14`의 헤더 주석은 16-B §4를 인용해 초기화 순서를
네 단계로 적어 둔다. Notion 원문 `16-B 구현·데이터 계약 §4`에도 이벤트 소비
기록 초기화가 빠져 있다면 원문을 함께 고쳐야 한다.
**Notion 수정은 ChatGPT/Codex 담당이므로 이 문서에서는 미결로만 남긴다.**

## 2. F-02 · 게임 본체에 번체중국어가 없다 (전시 기준과 불일치)

| | |
|---|---|
| 확실성 | **확정** |
| 영향도 | **높음 — 기획 결정 필요** |
| 성격 | 기획-구현 불일치 |

### 근거

```csharp
// Assets/Scripts/Localization/LocalizationManager.cs:31
public enum Language { Korean = 0, English = 1 }
```

번역표는 한국어 → 영어 **단방향 사전 하나**이고 항목은 213개다.

```csharp
// Assets/Scripts/Localization/LocalizationTable.cs:18-19
public static readonly Dictionary<string, string> Ko2En = new();
public static readonly Dictionary<string, string> En2Ko = new();
```

파일 머리에도 `한국어 → 영어 번역표 (해외 전시용)`이라고 적혀 있다.

반면 다른 산출물은 3개 언어를 전제한다.

- `README.md:8` — 게임명을 한국어·중국어 번체·영어로 정의
- `art/brand/README.md:7` — 브랜드 정본에 `怪異探查局` 포함
- `HANDOFF.md:11` — **"대만 전시가 기준"** 이라 랜딩 기본값을 번체중국어로 고정
- 랜딩 페이지는 세 언어를 모두 지원하고 번체중국어가 기본

즉 방문자는 랜딩을 번체중국어로 읽고 게임은 한국어나 영어로 플레이하게 된다.

### 판단이 필요한 지점

이건 버그가 아니라 **범위 결정**이다. 임의로 정하지 않고 선택지만 남긴다.

| 안 | 내용 | 비용 |
|---|---|---|
| A | 전시에서 게임은 영어로 시연하고 번체중국어는 랜딩까지만 | 추가 작업 없음. 관람객 경험이 반쪽 |
| B | 번체중국어를 게임에도 추가 | `Ko2En` 단일 사전을 언어별 구조로 바꾸는 리팩터링 + 213항목 번역 + 서체 |
| C | 부스에 번체중국어 안내물을 따로 두고 게임은 영어 | 중간 비용 |

B를 고르면 구조 변경이라 별도 스펙과 승인이 필요하다.
`HANDOFF.md:965`는 남은 로컬라이제이션 작업을 "언어별 서체 지정, 용어 사전
대조·원어민 검수, 동적 문자열 갱신 검증"으로 적어 두었는데, 여기에 세 번째
언어 지원 여부를 먼저 결정해 넣어야 한다.

## 3. F-03 · 이벤트 효과와 기록의 중복 방지가 서로 다른 층에 있다

| | |
|---|---|
| 확실성 | 확정(구조), **추정(도달 가능성)** |
| 영향도 | 낮음 — 프로토타입 6층에서는 도달하기 어렵다 |
| 성격 | 잠재 결함 |

### 근거

`EventService.ResolveChoice()` (`Assets/Scripts/Event/EventService.cs:48`)에는
자체 중복 가드가 없다. 주석이 구조를 그대로 설명한다.

```
// 재클릭·연타는 EventPanel 이 선택지를 숨겨 차단하고, 기록은 dedupKey 가 최종 안전망.
```

- **상태 효과**(HP·스트레스·영혼석)는 `EventPanel`이 선택지 행을
  `SetActive(false)` 하는 것으로만 막는다
- **수첩 기록**은 `dedupKey: choice_{evt.id}`로 막는다
  (`EventService.cs:84`)

`EventPanel.OnClosed()` (`Assets/Scripts/Event/EventPanel.cs:429`)는 블러만
반납하고 `_current`나 해결 여부 플래그를 비우지 않는다. `Bind()`
(`EventPanel.cs:135`)는 호출될 때마다 선택지 행을 다시 활성화한다.

따라서 같은 이벤트로 다시 진입하면 효과는 다시 적용되고 기록만 걸러진다.
`RunSessionManager`가 재사용하는 패널 인스턴스도 하나다
(`NodeSystem.cs:1200`).

### 도달 가능성이 낮은 이유

`EventCatalog.GetRandom()`이 뽑은 이벤트를 즉시 `_consumed`에 넣어
한 런 안에서는 다시 뽑히지 않는다. 정의된 이벤트가 19종이라
프로토타입 6층 런에서 후보가 소진돼 순환이 재시작될 일은 드물다.

**다만 F-01을 고치면 상황이 달라진다.** 소비 기록을 런마다 비우게 되면
후보 소진 자체는 여전히 드물지만, 두 가드의 비대칭은 그대로 남는다.

### 제안

효과 적용 지점에도 가드를 두어 두 층의 기준을 맞춘다. 예를 들어
`ResolveChoice` 진입부에서 `RunSessionManager`에 이미 기록된
`choice_{evt.id}`가 있으면 효과를 적용하지 않고 반환하거나,
`EventPanel`에 `_resolvedThisOpen` 플래그를 두고 `OnClosed`에서 비운다.

어느 쪽이 맞는지는 **같은 이벤트를 한 런에서 두 번 만났을 때 효과가
두 번 적용돼야 하는지**에 대한 기획 판단에 달려 있다. HANDOFF.md §3은
"재개방·재클릭·연타·재로딩으로 결과와 기록을 다시 만들지 않는다"고만 적어
두어 서로 다른 노드에서의 재조우는 다루지 않는다. **미결.**

## 5. 점검하지 못한 범위

시간과 환경 제약으로 아래는 **보지 않았다.** 다음 점검자가 이어받을 곳이다.

- `BattleManager` 4개 파일 약 2,600줄 — 전투 상태 전환, 턴 경계, 효과 중복
- `NodeSystem.cs` 1,241줄 — F-01 관련 진입점만 봤고 경로·층 진행은 미확인
- `PartyManager` / `MercenaryService` — 런 간 파티 상태 잔존 여부
- 스택·역할 시스템(`StackCardController`, `Stack/RoleCostBase`) — 핵심 기전인데 미확인
- 213개 번역 항목의 **커버리지** — 화면에 나오는 한국어 중 표에 없는 문자열이
  있으면 영어 시연에서 한국어가 그대로 노출된다. 기계적 대조가 가능하나
  실행하지 못했다
- 씬·프리팹의 Inspector 연결
- 저장·불러오기 계약

### 테스트 인프라 현황

`Packages/manifest.json:17`에 `com.unity.test-framework: 1.6.0`이 들어 있지만
**테스트 파일도 `.asmdef`도 하나도 없다.** 자동 테스트를 붙이려면 테스트
어셈블리부터 만들어야 하고, 이는 구조 변경이라 별도 승인이 필요하다.
HANDOFF.md:964의 다음 작업 6번(`이벤트 중복 방지·런 초기화 ... 자동 테스트`)이
바로 이 작업이며, F-01은 그 테스트가 있었다면 잡혔을 결함이다.
